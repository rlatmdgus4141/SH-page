## ① 무엇으로 붙였나

라이브러리 **SimpleWebAuthn server/browser 13.3.0**으로 WebAuthn 등록·서명 검증을 처리했습니다. 계정·패스키·질문·세션 저장과 접근 제어는 직접 구현했습니다. Sites의 HTTPS Worker와 D1 SQLite를 사용합니다. 앱에는 비밀번호 입력·비밀번호 DB·비밀번호 복구가 없습니다. 기기의 지문·얼굴·잠금 PIN은 기기에서 처리합니다.

서버는 COSE 공개키를 base64url로 저장합니다. 기기 개인키는 WebAuthn 응답에 포함되지 않습니다. 공개키로 로그인 서명을 검증합니다. 아래는 실제 A 계정의 등록 응답과 서버 목록에 포함된 COSE **공개키** 저장값입니다. 공개키이며 비밀번호·개인키가 아닙니다.

`pQECAyYgASFYIOw93ScQdKFq-hVUv__YNa_dzSDHmjhs1W4yN_4FH7e0IlggonSmBGfcsPLvRvwNo-QjyBy_5ojd474t0C2ZGWFXGLQ`

실제 등록 요청의 `clientDataJSON`·`attestationObject`는 공개 확인 자료 `T08_browser_registration.public.json`에, 실제 로그인 요청의 `authenticatorData`·`signature`는 공개 확인 자료 `T08_browser_security.public.json`에 있습니다. 요청 본문에 개인키가 없습니다. 쿠키·세션 원문도 보관하지 않았습니다. 로컬 소프트웨어 인증기의 요청·응답은 소스의 `t08/service-results.json`에 따로 구분해 보관했습니다. 패스키 저장 위치는 등록할 때 본인이 선택한 값이며 서버 자동 판별값이 아닙니다.

## ② 왜 그걸 골랐나

공개 소개를 유지하면서 패스키만으로 개인 공간을 열기 위해 선택했습니다. 암호 검증은 WebAuthn 전용 라이브러리를 사용하며 계정별 자료 접근은 서버에서 검증합니다. 이메일·비밀번호 복구를 우회 경로로 추가하지 않았습니다.

## ③ 어디를 어떻게 고쳤나

| 흐름 | 소스 | 처리 |
|---|---|---|
| 공개 소개 | `app/route.ts`, `lib/public-page.ts` | T01 내용에 개인 공간 UI를 추가. 비공개 메모는 HTML·JS에 넣지 않음 |
| 등록 | `public/passkeys.js` → `app/api/passkeys/route.ts` → `lib/passkeys.ts`의 `register-options/register-verify` | 서버의 난수 질문을 DB에 5분 보존하고 flow 쿠키에 연결. 검증 후에만 계정·공개키 저장 |
| 로그인 | 같은 경로의 `login-options/login-verify` | 새 질문과 저장 공개키로 서명 검증. 고정 Origin·RP ID·UV도 검증한 뒤 세션 발급 |
| 로그아웃 | 같은 경로의 `logout` | DB 세션 삭제, 쿠키 만료, 화면의 메모 제거 |
| 비공개 조회 | `app/api/private/route.ts` → `lib/passkeys.ts`의 `/api/private` | 세션 필수. 조회 SQL의 소유자는 서버 세션으로 정함. 다른 계정 쿼리는 403, 위조 본문 소유자는 무시하고 내 자료 반환 |
| 키 관리 | `delete-passkey`, `db/schema.ts` | 내 키만 삭제. 해당 키의 세션도 FK cascade로 폐기. 5분 이내 패스키 인증 필요 |

로그인 뒤 식별 수단은 **서버 세션**입니다. 32바이트 난수 토큰을 HttpOnly·Secure·SameSite=Strict·Path=/의 `__Host-t08_session` 쿠키에 넣습니다. DB에는 SHA-256 해시와 12시간 만료 시각만 저장합니다. 계정 별칭은 공개용 식별자이며 실명이 아닙니다. 요청 본문 소유자나 토큰을 세션으로 신뢰하지 않습니다. Origin·RP ID는 배포 주소에 고정합니다.

질문은 검증 시작 때 `DELETE ... RETURNING`으로 한 번만 소비합니다. 실패한 서명에도 다시 쓸 수 없습니다. 취소하면 현재 임시 질문을 지우고 계정·패스키는 생성하지 않습니다. 만료 임시 질문은 후속 발급에서 정리합니다.

AI에게 맡긴 일: T01 소개 보존, 패스키 인증·서버 접근 제어 구현, 확인 도구와 자동 검사, 설명서 작성.

AI 말을 따르지 않은 일: 별도로 없음. 제안을 실제 기기에서 실행해 결과를 확인한 뒤 반영했고, 로컬 검사와 실제 배포 근거는 구분했다.

## ⑥ 아직 못 막은 것

- 모든 키를 잃거나 삭제했을 때 **계정 복구를 제공하지 않습니다.** 마지막 키 삭제 후 자료는 남지만 재로그인이 불가능합니다. 화면과 삭제 확인 창에서 알립니다. 독립된 두 저장소의 키를 미리 준비해야 합니다.
- 이미 장악된 기기·브라우저의 유효 세션 사용을 완전히 막지 못합니다. 세션은 최대 12시간이고 키 관리에는 5분 이내 인증을 요구하지만 그 시간 안의 장악 위험은 남습니다.
- 저장소의 동기화·복구 정책은 앱이 통제하지 않습니다. `attestation: none`으로 제조사나 하드웨어 보안 등급을 증명하지 않습니다. 저장 위치도 자기 보고값입니다.
- IP+별칭별 15분 30회 제한은 여러 IP·별칭을 이용하는 분산 등록 공격을 완전히 막지 못합니다. 운영 시 전체 요청·저장량 제한과 감시가 필요합니다.
- 실제 브라우저 확인은 사용자의 이번 환경에 한정됩니다. 모든 OS·브라우저·보안 키 조합의 호환성이나 저장소 제조사를 검증하지 않았습니다.

`제출용 접근 차단 확인 도구`에서 실제 배포 API로 상대 계정 조회와 본문 소유자 위조를 검사할 수 있습니다. 다른 계정 로그인 검사는 서버가 발급한 상대 계정용 질문에 현재 계정의 실제 패스키로 서명합니다. 브라우저의 allowCredentials 목록을 바꾸더라도 서버는 질문에 연결된 계정의 키만 받아들입니다. 삭제한 키 검사도 같은 방식으로 기기에 남은 삭제 키의 실제 서명을 전송합니다. 서버가 키를 삭제했다는 이유만으로 기기에 남은 키가 지워지는 것은 아닙니다.

사용한 로그인 질문 검사에는 성공한 요청 본문을 그대로 재전송합니다. 이를 위해 성공한 로그인 뒤 flow 쿠키는 발급 때 정한 최대 5분까지만 유지합니다. 질문 행은 첫 검증 때 이미 소비되므로 동일 쿠키가 남아 있어도 두 번째 검증은 409입니다. 쿠키 원문은 JavaScript나 내려받기 기록에 공개하지 않습니다.

변조 서명 검사는 새로운 로그인 질문에 기기로 서명한 다음 서명의 첫 글자를 바꾸어 전송하고 401 거절을 확인합니다. 검사를 취소한 경우 통과로 기록하지 않습니다. 각 확인 결과는 해당 브라우저 창의 JSON에 포함됩니다.

로그아웃 응답의 `sessionReplay`는 **서버 내부에서 동일한 HttpOnly 쿠키로 실제 private API 처리 함수를 로그아웃 전·후 호출한 결과**입니다. 전·후 200→401을 보관하되, 브라우저에서 추가 HTTP 요청을 보낸 결과와 구분합니다. 응답에 쿠키 원문은 넣지 않습니다. 로컬 자동 시험에서도 같은 옛 쿠키를 다시 사용하는 독립 요청이 401임을 확인합니다.
